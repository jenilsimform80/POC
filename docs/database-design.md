# Database Design

Status: Phase 2 — schema designed in [backend/prisma/schema.prisma](../backend/prisma/schema.prisma). Migration applied (see "Migration status"). Prisma 7.10.0, PostgreSQL 14.

## Entities and relationships
```
users ─┬─< users (manager_id → users.id, "direct reports")
       ├─< time_entries >─ projects ─< tasks     (entry's task must belong to its project)
       ├─< project_members >─ projects           (only used when projects.is_restricted)
       ├─< task_assignees >─ tasks               (no rows = open to everyone)
       ├─< weekly_submissions ─< approvals >─ users (manager)
       ├─< locked_periods (locked_by)
       └─< audit_logs (actor)
```
| Table | Purpose | Key constraints |
|-------|---------|-----------------|
| users | Accounts and roles (`CONTRIBUTOR`, `MANAGER`, `ADMIN` = Admin/Finance) | unique email; `manager_id` self-FK; CHECK `manager_id <> id` |
| projects | Billable projects with a hour budget | unique `code`; CHECK `budget_hours >= 0`; CHECK `end_date >= start_date` |
| project_members | Who may use a restricted project (`projects.is_restricted`) | PK `(project_id, user_id)`; FK to project is `ON DELETE CASCADE` (membership rows are not financial data) |
| task_assignees | Who may log time to a task; no rows = everyone who can use the project | PK `(task_id, user_id)`; FK to task is `ON DELETE CASCADE` |
| tasks | Tasks within a project | unique `(project_id, name)`; unique `(id, project_id)` (FK target); `created_by_id` = manager who created it (null for admin-created) |
| time_entries | One row per user/project/task/day/hours | composite FK `(task_id, project_id)` → tasks; CHECK `0 < hours <= 24` |
| weekly_submissions | A user's submission of one week | unique `(user_id, week_start)`; CHECK week_start is a Monday |
| approvals | Append-only manager decisions on a submission | FK to submission and manager |
| locked_periods | Locked calendar months (global); a row = locked, deleting it = unlock (history in audit_logs) | unique `period_start`; CHECK first day of month |
| audit_logs | Structured trail of workflow actions | indexed by entity, actor, time; **append-only** (trigger `audit_logs_append_only`, SQLSTATE `LK002`) |
| sessions | Server-side login sessions (Phase 3) | unique `token_hash` (SHA-256 of the refresh token; the JWT access token names the row through its `sid` claim; rotated in place on refresh); FK to users is `ON DELETE CASCADE` (the one exception to RESTRICT: ephemeral data); indexed by user and expiry |

## Decisions
- **Delete behavior:** every foreign key is `ON DELETE RESTRICT`. Financial and audit data is never cascade-deleted. Users, projects and tasks are retired with `is_active = false` instead of being deleted. Time entries may be deleted by the application only while editable and unlocked (rule enforced in Phase 4/5). Audit logs are never deleted (a DB-level append-only guard is evaluated in Phase 5).
- **Manager model:** `users.manager_id` self-reference; each user has at most one direct manager. Managers may themselves have a manager (so their timesheet has an approver); the application refuses loops (checked under the user-administration lock). "Direct report" checks are `report.manager_id = manager.id`. A reporting-history table was rejected as unnecessary for timesheets-billing.
- **Lock model (Phase 2 scope):** one global row per calendar month. An entry is locked when a `locked_periods` row exists with `period_start = date_trunc('month', work_date)`. Unlock fields and the DB trigger are Phase 5 (they will be added in a new migration, never by editing this one).
- **Dates:** `work_date`, `week_start`, `period_start`, project dates are `DATE` (no time zone, no shifting by client or server zone). Event times (`created_at`, `locked_at`, ...) are `timestamptz`. Prisma returns `DATE` as a JS `Date` at UTC midnight; code must use UTC accessors/ISO strings. The reporting timezone policy is decided in Phase 6.
- **Week definition (assumption):** ISO week, Monday start (enforced by CHECK). Unverified against the original spec; changing it needs a new migration.
- **Hours:** `numeric(4,2)` (exact decimals, no float rounding), 0 < hours <= 24 per entry. Daily/weekly total limits and warnings are service rules (Phase 4), not DB constraints, because totals span rows.
- **IDs:** UUID primary keys generated by PostgreSQL (`gen_random_uuid()`, built into PG13+), so direct SQL inserts also get ids.
- **Email:** unique; the application lower-cases it before saving (case-insensitive uniqueness via `citext` was not added to avoid an extension in timesheets-billing).
- **Resubmission:** one `weekly_submissions` row per user/week whose `status` moves SUBMITTED → APPROVED/REJECTED → SUBMITTED again; every decision stays in `approvals`.
- **Indexes (initial, from expected queries):** `time_entries(user_id, work_date)` (timesheet view), `(project_id, work_date)` (project reports), `(work_date)` (monthly totals and lock checks), `weekly_submissions(status)` (approval queue), FK columns on approvals/users. Revisit with `EXPLAIN` in Phase 6.
- **CHECK constraints** are hand-added SQL in the migration because Prisma cannot declare them.

## Local database setup (you run this once)
Create a dedicated, non-superuser role and one database. Tests and e2e use a derived sibling `<name>_test`, created automatically by `npm run db:setup:test`. `CREATEDB` is required because `prisma migrate dev` creates a temporary shadow database.
```bash
sudo -u postgres psql <<'SQL'
CREATE ROLE timesheets WITH LOGIN PASSWORD 'choose-a-password' CREATEDB;
CREATE DATABASE timesheets_dev  OWNER timesheets;
SQL
```
Put the URLs in the git-ignored `backend/.env` (see `.env.example`):
```
DATABASE_URL=postgresql://timesheets:<password>@localhost:5432/timesheets_dev?schema=public
```
URL-encode special characters in the password. Tests and e2e run against `timesheets_dev_test` (derived from `DATABASE_URL`) and refuse any database not ending in `_test`.

## Inspecting data in pgAdmin 4
1. Right-click **Servers → Register → Server…**
2. General: name `timesheets-local`. Connection: host `localhost`, port `5432`, maintenance database `timesheets_dev`, username `timesheets`, the password you chose (tick *Save password* only on your own machine).
3. Browse **Databases → timesheets_dev → Schemas → public → Tables**; right-click a table → **View/Edit Data → All Rows**.
4. Useful checks (Query Tool, `Alt+Shift+Q`):
   - Constraints: `SELECT conrelid::regclass, conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE connamespace = 'public'::regnamespace ORDER BY 1, 2;`
   - Applied migrations: `SELECT migration_name, finished_at FROM _prisma_migrations;`
   - Indexes: `SELECT tablename, indexname, indexdef FROM pg_indexes WHERE schemaname = 'public';`

## Period locking and audit guards (Phase 5)
Migration `20261011160000_period_lock_and_audit_guards` (hand-written SQL, no table changes):
- `assert_period_unlocked(date)`: takes `pg_advisory_xact_lock_shared` on `'period_lock:' || 'YYYY-MM'`, then raises SQLSTATE `LK001` if a `locked_periods` row exists for that month.
- Trigger `time_entries_period_lock` (BEFORE INSERT/UPDATE/DELETE, per row): checks `OLD.work_date` (UPDATE/DELETE) and `NEW.work_date` (INSERT/UPDATE).
- Trigger `audit_logs_append_only` (BEFORE UPDATE/DELETE): raises `LK002`.
- Application lock/unlock takes the same advisory lock **exclusively** (`period-lock.service.ts`); the key text must stay identical on both sides.
- Prisma surfaces these as `PrismaClientKnownRequestError` (`P2039`/`P2010`) with the SQLSTATE in `meta.driverAdapterError.cause.originalCode` (see `errors/prisma-errors.ts`).
- Test data cleanup uses `TRUNCATE audit_logs` (DELETE is blocked by design).
- Limits: the table owner can disable the trigger or TRUNCATE; see ADR 0005.
Inspect in pgAdmin: `SELECT tgname, tgenabled FROM pg_trigger WHERE NOT tgisinternal;` and `SELECT * FROM locked_periods;`.
